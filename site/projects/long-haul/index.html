LONG HAUL · INDEPENDENT PROJECT · IN DEVELOPMENT

Work that survives its runtime

A machine’s spare memory is not automatically usable capacity. An agent saying “done” is not automatically a completed job. Long Haul makes both constraints explicit.

ProblemArchitectureTradeoffsStatus and evidenceInspect the code

Problem and contribution

I’m building Long Haul as an independent public project for heterogeneous local inference and reliable agent work. My contribution is the runtime and contract design that connects typed hardware resources, scheduling, persistent work identity, and independently checked acceptance. Project authorship and the implementation map make that scope inspectable.

Hosts have different memory, runtimes, and measured links. Models can change between sessions. A useful system must admit feasible work, retain evidence across interruptions, and distinguish an attempted solution from an accepted one.

How the parts fit

  1. Discover and normalize. Probes or labeled fixtures become typed vessels, resources, and measured links.
  2. Validate and plan. Runtime profiles and compatible evidence constrain scheduler candidates.
  3. Decide and execute. Crew positions, authority, and work contracts govern the attempt.
  4. Record and evaluate. Append-only events preserve history; independent evidence binds acceptance to an exact candidate.

Checkpoints can be rebuilt from the event history. A new model session can resume the work contract without treating a conversation transcript as durable memory.

The important tradeoffs

Feasibility before optimistic pooling. Memory is typed by device and placement; pipeline eligibility requires measured topology. This rules out convenient but misleading plans based only on summed RAM or VRAM.

External acceptance before self-reported completion. Separating the worker from the evaluator adds identities and evidence bookkeeping, but ties acceptance to the actual candidate and contract predicates.

Portable public runtime, separate operational control. The public repository contains runtime code and reference contracts. Concrete private Fleet machines and privileged promotion are outside it. Read the boundary ↗.

What exists, and what remains a question

The public implementation includes typed models, scheduler admission, append-only events, work contracts, checkpoints, and evaluator interfaces with focused tests. That is implementation evidence, not a claim of superior model performance.

The scheduler experiment plan asks whether a two-member, dissent-preserving scheduler improves on simpler baselines under matched constraints. That research question remains distinct from the implemented mechanisms. The north-star document describes the broader design, not a list of finished capabilities.

Start with one inspectable path

Follow an exact candidate through independent evaluation: read the work contract implementation, then the evaluator tests. The tests expose what is accepted, rejected, and tied to a specific candidate without needing private Fleet access.
