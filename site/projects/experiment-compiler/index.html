EXPERIMENT COMPILER · INDEPENDENT PUBLIC SOFTWARE

An inspectable path from source to artifact

A research result needs more than a ZIP of code. Its inputs, protocol, environment, run record, and interpretation need identities a reader can inspect.

ProblemArchitectureTradeoffsStatus and evidenceMinimal example

Problem and contribution

I created Experiment Compiler by extracting a deterministic packaging idea from my research tooling into a generic public compiler. It assembles declared source bytes and metadata into portable artifacts, verifies their inventory, and supports a separate bounded execution lifecycle. The origin record documents that contribution and the preserved first package.

The central constraint is to preserve what the source actually declares. Packaging must not invent a missing method, turn a run into scientific validation, or require access to a private research checkout.

How the parts fit

  1. Recipe and declared inputs. Source-owned recipes select files, metadata, and resource closure.
  2. Deterministic assembly. The compiler writes a ZIP, inventory manifest, and provenance.
  3. Offline verification. The verifier checks bytes and exact inventory without executing package members.
  4. Explicit execution and finalization. A bounded runner creates a new attempt; reviewed source interpretation belongs to a new result identity.
  5. Derived catalog. Public pages project the authoritative records and exact artifacts.

The important tradeoffs

Explicit inputs over inferred completeness. Resources are classified as embedded, immutable public, host prerequisites, or unavailable. Unknown required resources block execution admission rather than silently becoming defaults.

Separate assembly from execution. Compile and verify do not install dependencies, call the network, or train a model. The runner is a deliberate boundary with its own receipts.

New artifacts over rewritten history. Attempts, revisions, and finalization produce new identities. The historical compatibility fixture keeps its original bytes and limitations. The provenance uses existing standards including RO-Crate, PROV-O, Croissant, and CWL.

What the evidence establishes

The public compiler/verifier and lifecycle implementation are available with tests. The self-contained linear-regression fixture exercises packaging of implementation, synthetic data, protocol, and a reference result. The Muon walkthrough shows a real-study path while retaining the distinction between execution, interpretation, and independent reproduction.

The original compatibility package can be rebuilt byte for byte, but lacks the full inputs needed to independently replay its science. A passing package verification establishes integrity; it does not establish that a scientific conclusion is correct.

Compile and verify a small example

With Python 3.11 or later, run these commands from a checkout of the public repository. This packages and verifies the declared linear-regression fixture; it does not launch a training run.

python -m experiment_compiler compile examples/linear-regression-v1/experiment.json
python -m experiment_compiler verify dist/stdlib-linear-regression-v1-compiled-experiment.zip --recipe examples/linear-regression-v1/experiment.json
